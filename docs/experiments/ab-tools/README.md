# 按需激活 vs 全量注册：120 工具下的 A/B 实测

本目录保存 2026-10-20 在 DSH 宿主上做的三轮 A/B 实验（共 144 次运行）的原始数据与分析结论：固定 120 个工具、固定 `deepseek-flash`，只改变 `reasoningEffort`（off / low / high）。

**一句话结论**：在 120 个工具、`deepseek-flash` 下，YouMi 式「按需激活」在每一个推理档位上都更便宜，而且中间档位（`low`）省得最多。中位数口径：`off` 省 15%、`low` 省 **51%**、`high` 省 **28%**；均值口径对应的 26% / 38% / 5.5% 不可直接引用，因为 `high` 档的单次极端样本把均值拉扁了。代价是步数多 1.4–2.6 步，墙钟时间在 `off`/`high` 档多 33–34%、`low` 档基本持平。**成本优势是真实的，但它来自「长期平均」，不是每一次都省。**

## 要回答的问题

传统 MCP server 在 `initialize` 后一次性把所有工具的 schema 交给客户端，客户端再全量注册进 prompt 前缀。工具库一大，光「工具定义」就吃掉大量上下文，而且每一步都要为它付费。

YouMi 的做法是：进程内只常驻 2 个元工具（`youmi_tool_search` / `youmi_tool_get`），任务澄清后再检索，命中才把目标工具并入 `tools/list`，并通过 `notifications/tools/list_changed` 让客户端重新同步。

实验要验证：**这份「不把工具摊在上下文里」的节省，是否大于它引入的检索开销和缓存失效代价。**

## 实验条件

### 运行环境

| 项 | 值 |
|---|---|
| 宿主 | DSH 0.2.1-rc.2，`--profile headless --json`（NDJSON 事件流） |
| 模型 | `deepseek-account` / `deepseek-flash`，`maxTokens=256000` |
| 推理档 | 三档分别测：`reasoningEffort=off` / `low` / `high`（不配置时的默认档就是 `high`） |
| 工具量 | 120 个业务工具（12 个业务域 × 10） |
| 样本 | 每档 8 任务 × 2 组 × 3 轮 = **48 次**；三档共 **144 次** |
| 沙箱 | 每次运行独立的空目录，避免宿主文件系统给模型提供额外线索 |

模型与档位已从 session log 的 `request/header` 核对，三档分别为：

```
{"provider":"deepseek-account","model":"deepseek-flash","reasoningEffort":"off"}
{"provider":"deepseek-account","model":"deepseek-flash","reasoningEffort":"low"}
{"provider":"deepseek-account","model":"deepseek-flash","reasoningEffort":"high"}
```

三档之间唯一变化的配置项就是 `reasoningEffort`，其余（工具目录、prompt、沙箱、mock server 代码）完全一致。

### 实验装置

同一个 MCP server（`scripts/ab/mock_tool_server.py`），靠 `--eager` 开关切换两种形态，保证两组共用同一份工具目录、同一批 prompt：

- **A 组（全量注册）**：`--eager`，`tools/list` 一次返回全部 120 个工具。等价于 DSH 原生接一个传统 MCP server。
- **B 组（按需激活）**：默认形态，初始只返回 2 个元工具；`youmi_tool_search` 命中后把目标工具并入激活集，**先回响应、再推 `notifications/tools/list_changed`**。

B 组的动态注入在 DSH 侧是成立的，依据是 `dsh-mcp-client/lib/index.js`：客户端注册了 `listChanged.tools.onChanged → refreshTools()`（L602-608），`refreshTools()` 走 `listTools({cacheMode:"refresh"})` 强刷（L129），然后 `dispose()` 全部旧工具、再全量 `register()` 新工具（L150-153）。**即 `tools/list` 返回什么，客户端工具集就精确等于什么，可增可减。**

### 任务集

8 个「工具发现」任务（`scripts/ab/tool-tasks.mjs`），每个对应 120 个工具中唯一的正确工具，且周围有 2-3 个近义干扰项（试算 vs 真做、查询 vs 变更）：

| 任务 | 正确工具 | 干扰项示例 |
|---|---|---|
| t1-refund 发起订单退款 | `billing_refund` | `order_refund_preview`、`billing_refund_query` |
| t2-stock 查询可售库存 | `inventory_check` | `inventory_batch_query`、`inventory_snapshot` |
| t3-track 查询物流轨迹 | `logistics_track` | `logistics_signature_query` |
| t4-assign 转派工单 | `ticket_assign` | `ticket_escalate`、`ticket_merge` |
| t5-grant 授予员工角色 | `identity_role_grant` | `identity_role_revoke`、`identity_permission_check` |
| t6-cohort 生成留存报表 | `report_cohort` | `report_funnel`、`report_custom_query` |
| t7-blacklist 加入黑名单 | `risk_blacklist_add` | `risk_blacklist_query`、`risk_rule_toggle` |
| t8-sms 发送短信通知 | `notify_sms_send` | `notify_email_send`、`notify_push_send` |

**断言口径**：只看实际调用了哪个工具，不看模型怎么描述。`businessCalls.includes(expect) && exitCode === 0 && reason === "completed"` 才算命中。

B 组能否成功的前提是检索把正确工具递到眼前，所以先用 `scripts/ab/check_recall.py` 回检：8 个任务的正确工具全部落在 top-3 内，其中 6 个排第一。

### 指标口径

- **加权 token** = `未缓存输入 × 1 + 缓存读 × 0.25 + 输出 × 4`（DeepSeek 量级），只用于跨组比较相对成本，不代表账单金额。
- **均值 vs 中位数**：每档每组只有 24 个样本，且分布右偏（少数检索失控的样本会把均值拉得很高）。本报告**以中位数为主要口径**，均值同时列出以便对照差异。两者差距越大，说明尾部风险越重。
- **缓存率** = `缓存读 / (未缓存输入 + 缓存读)`。
- **注入次数** = mock server 推送 `tools/list_changed` 的次数（DSH 自身的 info 日志不进 stderr，由 mock server 打点）。

### 三档合并对比（关键表）

均值和中位数给出的结论差异很大，必须两个口径并列。**中位数是更可信的口径**，因为它剔除了少数失控样本的影响：

| 推理档 | A 命中 | B 命中 | A 加权均值 | B 加权均值 | 均值差 | A 加权中位 | B 加权中位 | **中位差** |
|---|---|---|---|---|---|---|---|---|
| `off` | 87.5% | 91.7% | 16 077 | 11 904 | −26% | 12 350 | 10 536 | **−15%** |
| `low` | 100% | 87.5% | 31 610 | 19 523 | −38% | 29 468 | 14 336 | **−51%** |
| `high` | 95.8% | **100%** | 34 243 | 32 348 | −5.5% | 30 992 | 22 299 | **−28%** |

| 推理档 | B 步数 | A 耗时中位 | B 耗时中位 | 耗时差 | B 检索次数 |
|---|---|---|---|---|---|
| `off` | 4.6 | 6.3s | 8.4s | +33% | 2.5 |
| `low` | 5.7 | 10.8s | 10.2s | −6% | 3.4 |
| `high` | 7.4 | 12.9s | 17.3s | +34% | 4.4 |

四个变量的走向各不相同，需要分开读：

1. **成本优势是 U 型，`low` 是谷底。** 中位数口径 `off` 只省 15%，因为推理关闭后 A 组也退化成 2.6 步就收工，基数本来就低；`low` 省一半；`high` 回落到 28%，因为 B 组检索次数从 3.4 涨到 4.4。
2. **B 组检索次数随推理深度单调上升：2.5 → 3.4 → 4.4。** 这是整条曲线的主控变量。推理越深，模型越倾向「换个关键词再检一次」，而每次命中新工具都触发一次 `list_changed`。
3. **均值在 `high` 档严重失真（−5.5% vs 中位数 −28%）。** 差距来自 `t5-grant B r1` 单次 98 509 的极端值；B 组 24 次运行里只要有 2–3 次检索失控，均值就被拉高三分之一。中位数 22 299 才反映「典型情况」。
4. **命中率不跟着推理深度单调走。** `off` 下 A 组分不清「查询 vs 变更」（87.5%）；`low` 下 B 组在 t7 上 3/3 全败（87.5%）；`high` 下反过来 B 组 100%、A 组在 t1 错选 1 次。三档里没有一组同时拿下最高命中率和最低成本。
5. **成本省了，时间基本没省。** `low` 档两者持平（甚至 B 略快 6%），但 `off` 和 `high` 档 B 组都慢 33–34%。省钱不等于省时间。

## 结论

### YouMi 这个架构好在哪

**1. 上下文占用是结构性的三分之一，不是靠压缩 prompt 省出来的。**

A 组把 120 个工具 schema 全部写进 prompt 前缀，B 组只写 2 个元工具。实测前缀 21 941 vs 6 796 token，**三档算出同一组数字**（见后面的缓存剖面交叉验证），说明前缀体积只由工具数决定。工具越多，这个比值越悬殊 —— 因为 A 组线性增长，B 组基本恒定。这一条是整套架构唯一不受推理档位扰动的收益。

**2. 每步都在省钱，省的是「重复读同一份工具定义」的钱。**

`low` 档看 A 组步数与节省的关系，单调性很清楚：t2 只跑 2.0 步就收工，只省 8%；t8 跑 4.0 步，省 53%；t1 跑 4.3 步，省 47%；t4 跑 5.0 步，省 62%。道理很直白：**A 组每多走一步，就要为那 21 941 token 的前缀再付一次钱；B 组每多走一步，前缀几乎不变。** t2 省得少，是因为检索的固定开销（多 2 步往返）几乎抵消了前缀差额。

但这条规律有一个前提：**检索不反复**。`high` 档的 t5 跑了 13.7 步，按「步数越多越省」应该省得最多，实际反而亏 75% —— 多出来的步数不是花在干活上，而是花在换关键词重检。步数本身不创造收益，**只有「不重复检索的步数」才创造收益**。

**3. 选择面从 120 降到 3，模型不用在噪声里翻找。**

A 组 24 次运行里有 10–13 次触发过错选（`low` 档 10 次、`high` 档 13 次），典型是选到 `risk_blacklist_query`（low 档×8、high 档×7）、`identity_permission_check`（×7）这类「操作语义相近但不是要做的那件事」的工具。B 组错选 11–12 次，但集中在检索候选本身质量不足的情况。

### 对比 DSH 原生全量注册，坏在哪

**1. 前缀缓存被自己打碎，这是最贵的代价。**

DSH 原生架构里工具集是不变的，prompt 前缀从第 2 步起稳定命中，实测未缓存输入常年只有 **165–230 token**（`low` 档）/ **181–220 token**（`high` 档），缓存率 97.6% / 98.9%。

按需激活每注入一批工具，`tools/list` 内容就变，客户端全量注销再注册，前缀随之失效。B 组步 3 的未缓存输入跳到 **838**（是步 2 的 2.1 倍，`low` 档）/ **884**（是步 2 的 2.2 倍，`high` 档），缓存率降到 93.1% / 93.3%。注入 3.4–4.4 次就是 3.4–4.4 次重建。**这份「动态注入税」是 DSH 原生架构完全没有的。**

**2. 每次都多花一次完整往返，延迟并没有真正降下来。**

B 组要 2.0–8.7 次检索，步数在三档上分别是 4.6 / 5.7 / 7.4，A 组是 2.6 / 4.5 / 4.8。耗时中位数：

| 档位 | A 耗时中位 | B 耗时中位 | 差 |
|---|---|---|---|
| `off` | 6.3s | 8.4s | +33% |
| `low` | 10.8s | 10.2s | −6% |
| `high` | 12.9s | 17.3s | +34% |

只有 `low` 档打平（甚至 B 略快 6%），而那还是建立在 t7 上 A 组试错跑到 22.2s 拉高均值的前提下。`high` 档最悬殊，t5 直接 **34.0s vs 19.1s**。省钱不等于省时间。

**3. 候选集小，选错就没有第二次机会 —— 但推理深度能补上一部分。**

t7 是最刺眼的证据，但只在 `low` 档成立：B 组 3/3 全败，每一次都只调了 `risk_blacklist_query`（查询命中情况）就收工，从头到尾没碰 `risk_blacklist_add`。而检索其实把 `add` 放进了 top-3（回检排第 2）。

同一份 prompt，`low` 档 A 组 100% 成功 —— 因为它看得见全部工具，先查一遍、再试规则、再试评分，7.3 步之后摸到了 `add`。**A 组是靠试错兜底的，B 组把这个兜底路径砍掉了。**

但这个结论在 `high` 档被推翻了：同样是 t7，B 组 3/3 全对，反而 **A 组**在 t1 上错了一次（选 `billing_refund_query` 而非 `billing_refund`）。合理的解释是：候选少并不是决定性缺点，**「候选少 + 推理浅」才是**。推理足够深时，模型能在 3 个候选里比出「查询 vs 变更」的差别；推理浅时，它需要一个足够大的候选池来试错。

**4. 检索质量成了单点故障。**

DSH 原生架构不依赖检索，工具全在，最坏情况是多试几步。按需激活把「能不能找到」这件事押在检索排序上：t6 上 B 组检索了 6.3 次、步数涨到 9.3，加权成本反而比 A 组高 **39%**。检索一旦没一次给到位，节省立刻被反复搜索吃掉。

**5. 成本与成功率是交换关系，不是同时改善。**

low 档 B 省 38%（中位数 51%）但命中率 87.5% vs A 的 100%；off 档把推理关掉后，两组命中率一起掉到 87–92%，成本同时降到 1/4。high 档反过来，B 拿到 100%，中位数省 28% 但均值只省 5.5%。**没有任何一档是「又便宜又准又稳」的。**

### 三档放一起看：推理深度决定「省多少」，但不决定「省不省」

把三档的加权成本差按推理深度排开（中位数口径）：

```
B 相对 A 的加权差（中位数）
  off    −15%   ███████
  low    −51%   █████████████████████████  ← 谷底
  high   −28%   ██████████████
```

**每一个档位 B 都更便宜，但便宜幅度差三倍多。** 成本差 ≈ `前缀节省 × 步数 − 检索往返 − 注入次数 × 前缀重建`：

- `off` 只省 15%：推理关闭后 A 组也只需 2.6 步，前缀节省没机会乘起来。
- `low` 省 51%：A 组步数涨到 4.5，而 B 组检索才 3.4 次，两边都在花但 A 组花得快得多。
- `high` 回落到 28%：B 组检索跳到 4.4 次、步数 7.4，注入成本开始反噬。

**这是一个 U 型，不是单调关系。** 两个相反的力在拉扯：推理越深，A 组为那 21 941 token 的前缀付的次数量级地增多（利好 B），但 B 组的检索往返也同时变多（不利 B）。在 120 个工具这个尺度上，前一股力在 `low` 之后就被后一股力追上了。

**默认档位的结论要改口。** DSH 不配 `reasoningEffort` 时跑的是 `high`。按中位数，B 组仍然省 28%；但按均值只有 5.5%，而且 24 次里有近一半落在 30 000 以上。换句话说：**默认配置下这个架构省钱依赖「不出事」——一旦某次检索失控（或推理绕进去），单次成本能高到 98 509，把几次的节省全吃掉。** 它提供的不是稳定收益，而是有尾部风险的期望收益。

**收益的前提是检索一次到位。** t1/t7 在 high 档仍然省 50% 以上，因为它们都是一次检索就命中目标；t5/t6 净亏 75%+，因为模型反复换了 5–9 次关键词。所以真正可操作的改进方向不是「少暴露工具」，而是**提高首轮检索的命中密度**（增大 top_k、把近义工具打包返回、给出「已无更多相关工具」的明确信号），从源头减少往返次数。

### 反转点在哪

收益 ≈ `(全量 schema − 常驻元工具) × 步数 × 缓存折扣`
成本 ≈ `检索往返次数 × (完整前缀读一次 + 输出检索参数) + 注入次数 × 前缀重建`

- **工具规模大 + 任务长**：收益占优。t1/t4/t8 省 16–62%，其中 `low` 档最稳定（47–62%）。
- **工具规模大 + 任务短（2 步收工）**：接近打平。t2 只省 6–8%。
- **检索反复失手**：净亏。t6 在 low 档反超 39%，在 high 档反超 76%。
- **近义工具密集 + 低推理档**：成功率崩塌。t7 B 组在 low 档 0%。
- **推理档位越高**：反转点越容易触发。同一任务 t5 在 low 档 B 仍省 20%，到 high 档反而亏 75%。

## 局限

必须说明的边界，否则上面的数字会被误读：

1. **测的是「按需激活」这个策略，不是 YouMi 的完整实现。** B 组的检索用的是 mock server 里简化的 IDF 关键词打分（`scripts/ab/mock_tool_server.py:_search`），不是 YouMi 真正的 `ToolStore` + 向量检索 + 锥形分层。结论对架构方向有效，对 YouMi 具体实现只能部分外推。
2. **工具是合成的。** 120 个工具的 schema 体积、描述详略由脚本生成，真实业务工具的 schema 通常更臃肿，那会放大 A 组的劣势；但真实工具描述也更准确，可能改善 B 组的检索。
3. **样本量小。** 每档 48 次，单任务只有 3 轮。t7 那种 3/3 全败虽像系统性失败，但 33pp 的波动幅度也可能来自小样本；`t5-grant B r1` 一个 98 509 的极端样本就能左右整个 t5 的均值，三档均未做显著性检验，数字应读作方向性结论而非精确值。
4. **只测了一个工具规模（120）。** 400 / 1000 工具下的反转点没有实测，只是从公式推断。理论上工具越多 A 组前缀越贵，B 组的相对优势会扩大，但检索准确率也会随目录变大而下降，两个效应同向拉扯。
5. **只测了三档 `reasoningEffort`，`max` 未测。** 按趋势外推，`max` 档下 B 组的检索次数会继续上升（2.5 → 3.4 → 4.4 → ?），节省幅度可能从 28% 进一步收窄，甚至转为净亏。
6. **`high` 档已补测，但早期一轮作废数据不包含在内。** 早前跑过一轮 high，当时 mock 工具只回 `{"ok": true}`，模型拿不到业务数据就转去文件系统里摸索，步数涨到 22 步，与本轮不可比，已丢弃。当前 `report-high.txt` 与 `results-tools-high.jsonl` 是修复回执后重跑的那一轮。

## 复现

```powershell
# 档位由 scripts/ab-credentials.patch.yml 的 reasoningEffort 控制（off / low / high / max）
# 想跑另一档只需改这一行，然后重跑

# 单任务试跑（A 组全量 + B 组按需）
node scripts/ab-tools.mjs --repeat 1 --only t1-refund

# 完整 48 次
node scripts/ab-tools.mjs --repeat 3 --catalog-size 120

# 出报告（不要用 PowerShell 的 > 重定向，会写坏中文，用 --out）
python scripts/ab-tools-report.py --file .ab/results-tools.jsonl
python scripts/ab-tools-report.py --file .ab/results-tools.jsonl --out report.txt

# 回检 B 组检索是否把正确工具递到了眼前
python scripts/ab/check_recall.py
```

三档的复现顺序：改 `reasoningEffort` → 跑 48 次 → `Copy-Item .ab/results-tools.jsonl docs/experiments/ab-tools/data/results-tools-<档位>.jsonl` → 用 `--out` 生成 `report-<档位>.txt`。注意驱动每次启动会清空 `.ab/results-tools.jsonl`，上一档的数据必须及时拷走。
